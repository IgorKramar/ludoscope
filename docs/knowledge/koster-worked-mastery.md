# Пример: практика, повторная попытка и перенос навыка

Это оригинальный пример LUDOSCOPE, а не пример из книги Костера. Он показывает проверку структуры учебного плана и подготовку исследования. Игроки в нём не участвовали; улучшение обучения не измерялось.

## Проектный вопрос

В небольшой игре об исследовательском роботе автор хочет, чтобы игрок учился читать сигналы и выбирать маршрут с ограниченным запасом энергии. После ошибки можно быстро повторить задачу. Числовое усиление робота для этого эксперимента отключено: проверяется применение правила, а не покупка дополнительного запаса.

Дизайнерская гипотеза: практика с понятной причиной результата и новая конфигурация знакомых правил помогут отличить применение принципа от запоминания маршрута. Это `DESIGN_HYPOTHESIS`, а не установленный результат обучения.

## Первый вариант плана

Вход `ludoscope_mastery_analysis` содержит массив `skills`; порядок открытия задаёт `introduced_at`. Текстовые поля `practice` и `variation` описывают возможности, но инструмент не выполняет их и не подтверждает качество написанного.

```json
{
  "skills": [
    {
      "id": "skill.read_signal",
      "requires": [],
      "introduced_at": 1,
      "practice": ["Повторить один и тот же показ безопасного маршрута."],
      "variation": ["Изменить положение цели."]
    },
    {
      "id": "skill.plan_route",
      "requires": ["skill.read_signal"],
      "introduced_at": 0,
      "practice": ["Повторить сохранённый маршрут до успеха."],
      "variation": []
    },
    {
      "id": "skill.revise_plan",
      "requires": ["skill.plan_route"],
      "introduced_at": 2,
      "practice": [],
      "variation": []
    }
  ]
}
```

В реально выполненном вызове общего ядра `mastery(...)` получены четыре замечания:

```text
skill.plan_route precedes prerequisite skill.read_signal
skill.plan_route: no transfer or variation specified
skill.revise_plan: no explicit practice
skill.revise_plan: no transfer or variation specified
```

Результат имеет `claim_type: EXPERT_INFERENCE` и ограничение `Instructional plan only; mastery and cognitive load require observed users.` Проверка обнаруживает порядок известных зависимостей и пустые списки. Она не устанавливает, запомнит ли игрок первый маршрут, поймёт ли значок или будет ли практика полезной.

```json
      "practice": [
        "Выбрать путь при видимом ограничении запаса; получить причину расхода и повторить с теми же возможностями."
      ],
      "variation": [
        "Новая топология комнаты при том же правиле расхода и без усиления персонажа."
      ]
    },
    {
      "id": "skill.revise_plan",
      "requires": ["skill.plan_route"],
      "introduced_at": 2,
      "practice": [
        "После неудачного выбора указать предположенную причину, изменить одно решение и повторить задачу."
      ],
      "variation": [
        "Новая комбинация известных сигналов и ограничений; расположение маршрутов не совпадает с тренировкой."
      ]
    }
  ]
}
```

Повторный реальный вызов того же ядра вернул `issues: []` с тем же ограничением. Это означает, что в описании нет обнаруженных структурных проблем: предпосылки открываются вовремя, практика и вариации указаны. Непустой текст не доказывает ни реальную доступность практики в сборке, ни обучение, ни перенос навыка.

Проверку ядра можно повторить после `npm run build` из корня пакета, импортировав `mastery` из `./dist/analysis/labs.js` и передав каждый показанный объект. MCP использует те же поля входа; перед вызовом следует прочитать фактическую схему доступного инструмента. Дополнительный контекст знаний в ответе MCP не расширяет доказательную силу структурной проверки.

## Следующий эксперимент

Это план исследования, а не отчёт о проведённом плейтесте.

1. **Вопрос:** способен ли участник использовать правило оценки расхода на незнакомой карте, а не только воспроизвести тренировочный маршрут?
2. **Условия:** одна версия правил и управления, одинаковый запас энергии; новое расположение путей и знакомый словарь сигналов. Заранее проверить, что новая задача не требует дополнительного скрытого навыка.
3. **Процедура:** самостоятельная первая попытка, показ понятной причины исхода, повторная попытка, затем новая вариация. Любую помощь наблюдателя отмечать отдельно. При сравнении вариантов плана учитывать опыт участников и порядок предъявления.
4. **Наблюдения:** выбранный маршрут, использованная информация, ошибки чтения сигнала, исправление после обратной связи и применение принципа в новой конфигурации. Рассказ участника после задачи хранить отдельно от лога действий.
5. **Критерий интерпретации:** успех на прежнем маршруте совместим с запоминанием. Успех на новой карте при тех же возможностях, объяснение использованного ограничения и корректировка после ошибки дадут ограниченную поддержку гипотезе применения принципа. Они не докажут устойчивого переноса на любые карты.
6. **Альтернативные объяснения:** новая карта проще; участник уже знаком с подобной игрой; помогло управление; правильный выбор случаен; цвет, геометрия или подсказка выдали ответ. До сбора данных определить, как различать эти объяснения.
7. **Отчёт:** указать фактическое число уникальных участников и сессий, версию, условия, помощь и пропуски. Размер выборки здесь не выдумывается; независимое статистическое обобщение без соответствующего дизайна не предполагается.

Нулевая структурная ошибка плана и реальные наблюдения обучения должны оставаться разными результатами. Потребность в новой вариации также не обязывает автора бесконечно добавлять системы: можно менять контекст освоенных правил и отдельно сохранять желаемый спокойный ритм.
