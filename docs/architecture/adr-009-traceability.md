# ADR-009 — явная трассировка требований и файлов

**Статус:** принято для реализации 0.6.0.  
**Область:** design–code traceability, общий core, CLI и MCP.  
**Связанные решения:** [ADR-003, ADR-005, ADR-007 и ADR-008](decisions.md).

## Контекст

У проекта уже есть граф игровых систем, ссылки на артефакты и контроль целостности доказательств между итерациями. Эти механизмы не отвечают самостоятельно на вопрос, сохранились ли файлы, к которым привязана механика, и существует ли объявленная цепочка от требования до свидетельства проверки.

Автоматически вывести смысл реализации из названий файлов нельзя. Совпадение Git HEAD не гарантирует неизменность рабочей копии. Наличие тестового файла не удостоверяет его выполнение и не устанавливает соответствие поведения авторскому замыслу.

Пилот на внешнем игровом проекте должен быть полезен даже тогда, когда доступны только исходники, а утверждённые требования, автоматизированные тесты и пользовательские наблюдения отсутствуют.

## Решение

Вводится строгий manifest 1.0 со стабильным ID, необязательной полной Git-ревизией, файловыми артефактами и явно объявленными связями.

Фиксируются пять этапов:

```text
requirement → mechanic → implementation → automated_test → playtest
```

Связь соединяет только соседние этапы в прямом направлении. Отсутствующий этап не заменяется прямой ссылкой через него. Структурные ошибки — дубликаты, неизвестные ID и неправильные переходы — отклоняются до файлового аудита.

Каждый артефакт получает относительный путь и SHA-256 полного файла. Необязательный диапазон строк уточняет локатор, но не ограничивает хеширование. Это консервативное решение: изменение любой части файла требует повторного рассмотрения привязки.

Общая функция `auditTraceability(root, input, signal?)` используется CLI и MCP. CLI разрешает путь manifest относительно своего рабочего каталога, а пути артефактов — относительно проверяемого корня. Сам manifest можно хранить отдельно от внешнего репозитория. MCP использует настроенный при запуске корень и получает manifest как данные.

## Два уровня результата

**Объявленное покрытие** отражает граф, предоставленный вызывающей стороной. **Актуальное покрытие** требует полного пути через пять этапов, на котором каждая файловая привязка совпадает с текущим содержимым.

Проверка возвращает отдельные статусы файлов и Git-ревизии. Устаревший исходник не переписывает исторический результат теста; актуальность их связи должен пересмотреть автор. `PROJECT_FACT` относится к наблюдаемой файловой проверке, а не к истинности содержимого документов.

Общий `complete` требует хотя бы одного требования, актуальных привязок всех артефактов, актуальной полной цепочки для каждого требования и отсутствия артефактов, недостижимых от требований. При закреплённой ревизии также нужны совпавший HEAD и чистое проверенное состояние Git. Без закрепления Git не вызывается.

Manifest без требований принимается для аудита одних исходников, но возвращает `partial` с пустым покрытием. Полнота не возникает из проверки пустого набора требований.

## Альтернативы и компромиссы

| Подход | Решение и причина |
| :--- | :--- |
| Выводить связи из имён файлов или классов | Не выбран: это создавало бы неподтверждённую семантическую трассировку |
| Использовать только Git commit hash | Недостаточно: содержимое рабочей копии может отличаться от HEAD |
| Хешировать только указанный фрагмент | Отложено: окружающий код может менять поведение, даже если фрагмент неизменен |
| Требовать все пять этапов при загрузке manifest | Не выбрано: это блокировало бы честный аудит неполного проекта |
| Считать manifest без требований полностью проверенным | Не выбрано: пустое покрытие не подтверждает путь от замысла до результата |
| Запускать команды тестов из manifest | Не выбрано: чтение свидетельств и разрешение исполнения — разные действия |
| Автоматически обновлять хеши при расхождении | Не выбрано: новый хеш требует пересмотра смысла связанной записи |

Полное хеширование может отмечать изменение комментария или несвязанного участка как устаревшую привязку. Это ожидаемая цена простого проверяемого механизма; аудитор не выдаёт такой сигнал за доказанный дефект игры.

## Границы исполнения

Чтение ограничено 100 артефактами, 500 связями, 2 MiB на файл и 20 MiB на весь аудит. Повторяющийся путь использует прочитанный снимок в пределах вызова; резервирование бюджета консервативно.

Пути ограничены заданным корнем; существующие символические ссылки и выход за корень блокируются. Файлы читаются последовательно, поэтому аудит не является атомарным снимком при конкурентном изменении репозитория. Используется доверенный локальный каталог.

При наличии `revision` разрешены только фиксированные ограниченные проверки Git HEAD и состояния. Команды из manifest, игровой код, тесты и сетевые обращения не выполняются. `AbortSignal` позволяет прервать библиотечный вызов на предусмотренных границах операций.

Аудит не изменяет исходники, manifest, авторский канон или утверждённые решения. Согласование новой спецификации и запуск новых тестов остаются отдельными действиями.

## Проверяемые свойства

При реализации и выпуске нужны проверки:

- корректная цепочка, недостающие этапы и недостижимые от требований артефакты;
- source-only manifest с пустым покрытием и `partial`;
- изменение файла, отсутствие файла, неверный локатор и бинарный файл без локатора;
- дубликаты, неизвестные ссылки и попытки пропуска этапов;
- traversal, символические ссылки, ограничения чтения и отмена;
- закреплённая и незакреплённая ревизия, несовпавший HEAD и изменённая рабочая копия;
- общий результат через библиотеку, CLI и MCP.

Этот список задаёт обязательства реализации, а не утверждает, что тесты уже запускались. Фактические результаты относятся к конкретному проверенному коммиту и фиксируются отдельно.

## Пересмотр решения

Вернуться к контракту при появлении подтверждённой потребности в других типах связей, семантической проверке реализации, больших репозиториях, подписанных результатах тестов или атомарных снимках. Расширение не должно менять смысл существующих `current` и `complete` без новой версии схемы.
